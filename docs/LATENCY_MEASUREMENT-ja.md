# 等倍での遅延測定（2026-09-14）

バイキュービックを既定に変更し、同じ補間指定・100%（等倍）表示で変更前後を比較した。

この条件ではp95が4MHzで約7.9ms、8MHzで約3.2ms短縮した。8MHzの中央値も約6.5ms短縮した。
4MHzの中央値は約0.6ms増加しており、すべての指標が改善したわけではない。
前回の150%測定は[拡大時の参考値](LATENCY_150_REFERENCE-ja.md)として分離した。測定条件を修正しただけで、今回アプリの実装は変更していない。

| CPU | 中央値：変更前 → 変更後 | p95：変更前 → 変更後 |
| --- | ---: | ---: |
| 4 MHz | 37.03 → 37.61 ms | 57.10 → 49.21 ms |
| 8 MHz | 43.58 → 37.05 ms | 54.66 → 51.46 ms |

p95は120試行中の114番目。中央値だけで改善を判定せず、遅い側の値も併記した。
平均は4MHzで40.01→37.13ms、8MHzで41.13→36.74msだった。

## 条件

- 基準：main `7dbbdc7607f880af90c9948f7c6ed1d39a73e0e6` のWin32実装。
- Windows x64 / MSVC RelWithDebInfo、同じN88V1H ROM、BASICの同じ位置にAキーを注入。
- 各CPU・各実装60回×2セット。4MHzは前→後→後→前、8MHzは後→前→前→後の順で実行。他の測定やビルドは並行実行しない。
- 開始はKeyDown呼び出し直前、終了はAの字形を含む描画関数から戻った時点。点滅カーソルは字形比較から除外。
- 同じベンチマークと共通コアを使用し、Win32実装・描画関数はそれぞれの版を使用。
- 非表示ウィンドウでのソフトウェア経路の測定。物理入力、DWM、モニター、音声デバイスの遅延は含まない。
- 両方ともバイキュービック指定だが、等倍では現行版のDIB直接転送経路を通る。拡大縮小用の補間計算は不要。
- 測定対象と同じ実装の配布exeのSHA-256：`97B88282E470982F72BB9D084A2DDCBC2B1FCC077BA4958F2EE4700BE7C50992`。

## 実装と検証

- キーイベントを即座に反映し、VSyncでUIの応答を待つ処理を廃止。
- QPCと中断可能な期限待機、命令超過の繰越、停止・速度変更の同期を導入。
- 変更領域のRGB変換、補間係数・作業領域の再利用、SSE2による補間、DIB転送を使用。
- 1ms単位実行とDMA完了コールバックは遅延改善を確認できず不採用。共通コアは変更していない。
- 14件の自動テスト。補間値・一定色・縮小時のエイリアス・画面端・下部バー保護・入力・待機を確認。
- 4MHz・8MHzの実ROM起動、停止・再開、クロック／速度切替、3種類の補間、終了を非表示で検証。

## 再測定

```text
native_input_latency_bench.exe <ROMディレクトリ> result.csv 60 8 2 100
```

引数は試行回数・MHz・補間（0/1/2）・倍率%。比較用のソースをエクスポートし、CMakeの`M88V_LATENCY_BASELINE_DIR`に指定すると`native_input_latency_before`も生成される。

等倍の生データと実行ログはローカルの`build/rom-validation/measured-*-100-*.csv` / `*.log`、集計は`summary-100.json`に保存。ROMはリポジトリに含めない。
